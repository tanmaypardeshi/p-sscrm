# Development guide

This is the technical rundown for anyone working on this site's code — not the framework content itself, just the website.

## Requirements

- [Hugo](https://gohugo.io) (extended version, currently built/tested against `0.162.1`)
- Python 3 (only needed to run the data sync script — stdlib only, no `pip install` required)

## Running locally

```
hugo server
```

Open the URL it prints (usually `http://localhost:1313/`). It live-reloads as you edit files.

To do a full production-style build (what actually gets deployed):

```
hugo --gc --cleanDestinationDir
```

Output goes to `public/` (gitignored, not committed).

## Repo layout

- `content/` — the text on every page, one markdown file per page.
- `layouts/` — Hugo templates that decide how each type of page looks.
- `assets/css/main.css` — all site styling, one file, plain CSS (no preprocessor).
- `assets/js/` — the small amount of JS the site uses (currently just the back-to-top button).
- `data/` — structured data (YAML) the templates read from, separate from page content.
- `static/` — files copied to the site as-is (images, etc.).
- `config/` — Hugo config, split by environment (`_default`, `development`, `production`).
- `scripts/sync_data.py` — pulls framework data from GitHub. See below.

## Content: generated vs. hand-written

Most of `content/` is hand-written markdown you edit directly — `about.md`, `contact.md`, `faq.md`, `frameworks.md`, etc.

**Three folders are the exception**: `content/groups/`, `content/practices/`, and `content/controls/`, plus `data/frameworks.yaml` and `data/versions.yaml`. These are entirely generated by `scripts/sync_data.py` from two upstream GitHub repos — [p-sscrm/p-sscrm](https://github.com/p-sscrm/p-sscrm) (the framework itself) and [p-sscrm/ats-to-ts](https://github.com/p-sscrm/ats-to-ts) (MITRE ATT&CK mapping). Every generated file starts with an `# Auto-generated ... do not edit by hand.` comment as a reminder.

Never hand-edit those — the next sync will silently overwrite whatever you changed. If the framework content itself is wrong, the fix belongs in the `p-sscrm/p-sscrm` repo (open a PR there), not here.

To pull the latest data:

```
python3 scripts/sync_data.py
```

Then review what changed with `git status` / `git diff` before committing — this is a manual step, nothing runs it automatically.

### A front-matter quirk

Hand-written pages (`about.md`, `faq.md`, `versions.md`, ...) use TOML front matter (`+++`). Generated pages (groups/practices/controls) use YAML front matter (`---`). Hugo supports both per-file; this is just a leftover of how the content was originally authored versus how the sync script writes files. Not worth "fixing" — just don't be surprised by it.

## Styling conventions

- Design tokens (colors, fonts, spacing) are CSS custom properties in `:root` at the top of `assets/css/main.css` — use them instead of hardcoding values.
- CSS and JS live under `assets/`, not `static/`, so Hugo's asset pipeline fingerprints them (content-hashed filenames) for cache-busting on every deploy. If you add a new stylesheet or script, put it in `assets/` and reference it via `resources.Get ... | fingerprint` in a template (see `layouts/partials/head.html` or `layouts/_default/baseof.html` for examples) — don't drop files straight into `static/css` or `static/js`.

## Deploying

Pushing to `main` triggers `.github/workflows/hugo.yml`, which builds the site with Hugo and publishes it to GitHub Pages automatically. There's no staging environment — whatever's on `main` is what's live.
